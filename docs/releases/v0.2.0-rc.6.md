# z2000 0.2.0-rc.6

This release candidate is about encode speed, with decode faster once more.
TIFF-to-JP2 encodes about a third faster than rc.5 and JP2-to-TIFF decodes
9-22% faster; on one thread z2000 now encodes as fast as Kakadu 8.4.1 and
decodes faster. Codestreams and decoded samples are byte for byte those of
rc.5 on every stream we test. One fix: the threaded 9/7 transform of a
one-row level at an odd vertical origin.

## Faster Encode And Decode

On an Intel Core i5-14500 (2048x2048 RGB, 8 bits), against rc.5 (medians of
interleaved runs on the same files; the lossless encode is the benchmark
profile with BYPASS, the lossy one two rate layers):

| Operation | Threads | rc.5 | rc.6 | Change |
| --- | ---: | ---: | ---: | ---: |
| lossless encode | 20 | 121 ms | 83 ms | -32% |
| lossless encode | 1 | 788 ms | 485 ms | -38% |
| lossy encode | 20 | 137 ms | 85 ms | -38% |
| lossy encode | 1 | 778 ms | 515 ms | -34% |
| lossless decode | 20 | 80 ms | 73 ms | -9% |
| lossless decode | 1 | 599 ms | 468 ms | -22% |
| lossy decode | 20 | 81 ms | 72 ms | -11% |
| lossy decode | 1 | 581 ms | 491 ms | -15% |

Against the other codecs, each with its own file of the same image
(`tools/bench_compare.ps1`, mean of 8 runs; one-thread rows give the range
of the three runs the two invocations made; lossy files of 4.80-4.83 MB):

| Operation | Threads | z2000 | Kakadu 8.4.1 | OpenJPEG 2.5.4 | Grok 20.4.19 |
| --- | ---: | ---: | ---: | ---: | ---: |
| lossless encode | 20 | 82 ms | 70 ms | 125 ms | 137 ms |
| lossless encode | 1 | 469-483 ms | 506-507 ms | 745-752 ms | 761-787 ms |
| lossless decode | 20 | 74 ms | 68 ms | 106 ms | 117 ms |
| lossless decode | 1 | 454-486 ms | 581-595 ms | 640-649 ms | 598-617 ms |
| lossy encode | 20 | 81 ms | 68 ms | 128 ms | 159 ms |
| lossy encode | 1 | 498-511 ms | 507-526 ms | 692-727 ms | 795-801 ms |
| lossy decode | 20 | 84 ms | 76 ms | 110 ms | 154 ms |
| lossy decode | 1 | 464-502 ms | 579-582 ms | 605-616 ms | 612-633 ms |

Details are in `docs/benchmarks.md`.

- **Tier-1 without branches on the coded decision**: the MQ encoder and
  decoder pick the sub-interval, the context's next state, and the
  renormalization shift by selects (a context that stays is not rewritten),
  and BYPASS bits are written the same way; refinement decisions are close
  to random, so the branches mispredicted on a large share of them.
- **Significance passes skip significant samples**: encoder and decoder
  visit only the stripe columns and rows not yet significant, by the
  significance bitmap (three quarters of the samples the pass examined in
  the lower bitplanes).
- **Encoder on all threads**: the lossy front end (ICT bands, quantization
  in place), the forward 5/3 and 9/7 on up to sixteen workers, the TIFF
  input's sample conversion and file read, and Tier-1 on the shared worker
  pool; each block is coded from a contiguous copy.
- **Less copying in the encoder**: the packet stream and the codestream are
  built into buffers of their final size, an RGB JP2 is written as its
  boxes and then the codestream, the rate allocation's probe builds packet
  headers only and its convex hulls once, and the coefficient planes are
  released in the background.
- **Shorter lossy decode tail**: the finest 9/7 level and the inverse ICT
  run in row bands straight into the TIFF buffer, as the lossless tail
  does, and the 9/7 transform runs on the shared pool.

## Fixes

- **Threaded 9/7 on a one-row level.** At an odd vertical origin a level one
  row high was transformed only in its last column band on several threads,
  so the threaded 9/7 differed from the serial one there. It takes a level
  at least 64 samples wide and one row high at an odd origin, which none of
  the test streams has; the parallel-versus-serial test now covers it.

## Release Process

- As for rc.5, every archive was built and tested on a local machine:
  native Windows gates, and the Linux x86-64 and RISC-V 64 ReleaseFast suites
  in a Linux container (RISC-V under QEMU), with the official T.803 streams
  included in the corpus run (`tools/release_local.ps1`).
- **No macOS archive** is published for this candidate: hosted Actions
  minutes, which the native macOS build needs, are exhausted, and a
  cross-built binary could not be tested here. macOS users can build from
  source with Zig 0.17.

## Release Candidate Policy

The CLI and Zig API remain unstable before 1.0. This is not a general JP2/JPX,
camera RAW, or HDR converter. Each input adapter has a deliberately narrow
documented envelope; old-style or progressive JPEG, CCITT, LZMA, and ZSTD
TIFF compression, Adam7 PNG, CFA/demosaicing, compressed or tiled EXR,
general ICC transforms, extended XMP, and semantic metadata rewriting remain
unsupported. JP2 metadata payloads are preserved but are not yet restored into
TIFF output.

The project's 100/100 ISO engineering scorecards are internal coverage tools,
not formal ISO conformance certification; passing the T.803 streams is
evidence, not certification. The binaries are unsigned; verify the platform
archive against `SHA256SUMS`. Every archive contains identical `z2000` and
`z2k` executables for the long and short command names.
