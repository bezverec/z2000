# z2000 0.2.0-rc.5

This release candidate is about decode speed. JP2-to-TIFF decodes faster on
one thread and markedly faster on many, with output byte for byte that of
rc.4 on every stream we test; irreversible 9/7 components now decode at
every Part 1 precision, and the wide (above 29-bit) encoder runs on all
threads.

## Faster Decode

On an Intel Core i5-14500 (2048x2048 RGB, 8 bits), against rc.4
(medians of interleaved runs on the same files):

| Decode | Threads | rc.4 | rc.5 | Change |
| --- | ---: | ---: | ---: | ---: |
| lossless 5/3 | 20 | 124 ms | 81 ms | -35% |
| lossless 5/3 | 1 | 812 ms | 612 ms | -25% |
| lossy 9/7 | 20 | 127 ms | 80 ms | -37% |
| lossy 9/7 | 1 | 789 ms | 597 ms | -24% |

Against the other codecs, each decoding its own file of the same image
(`tools/bench_compare.ps1`, mean of 8 runs; lossy files of 4.80-4.83 MB):

| Decode | Threads | z2000 | Kakadu 8.4.1 | OpenJPEG 2.5.4 | Grok 20.4.19 |
| --- | ---: | ---: | ---: | ---: | ---: |
| lossless 5/3 | 20 | 80 ms | 78 ms | 115 ms | 121 ms |
| lossless 5/3 | 1 | 609-627 ms | 610-681 ms | 678-914 ms | 648-660 ms |
| lossy 9/7 | 20 | 87 ms | 77 ms | 120 ms | 162 ms |
| lossy 9/7 | 1 | 594-604 ms | 601-618 ms | 624-631 ms | 646-652 ms |

Encode is 13-15% faster too (lossless 138 -> 118 ms at 20 threads, 1037 ->
900 ms at one), with byte-identical output. Details are in
`docs/benchmarks.md`.

- **Tier-1 on one thread**: folded MQ contexts, a 64-bit MQ register that
  renormalizes in one shift, a cleanup pass that screens four rows of a
  column at once, and neighbor flags written a row at a time.
- **Stages overlap Tier-1**: one block pool decodes all components, and the
  inverse 5/3 or 9/7 of each finished plane runs inside it while later
  planes still decode. One process-wide worker pool serves every parallel
  stage and starts while the input is read.
- **Shorter head**: the packet scan, the packet-header walk, the catalog
  fill, and the coverage check run on all threads; a single-layer stream's
  block payloads stay in the input instead of being copied.
- **Shorter tail**: 8-bit RGB is written straight into the TIFF buffer; a
  reversible decode finishes the last plane's finest wavelet level and the
  colour transform in one pass over row bands; irreversible planes are
  dequantized in place; large intermediates are released in the background
  while the file is written; the JP2 wrapper's tile-part audit runs beside
  the decode.
- **Less memory**: a lossy 2048x2048 RGB decode no longer holds a second
  48 MB of floating-point planes, and the block catalog shrank from about
  1 KB to under 200 bytes per code-block.

Every change keeps the decoded samples identical: the corpus, the
ITU-T T.803 streams, region and quality-layer decodes, the 34-bit wide
stream, and mutation tests that compare one-thread with eight-thread
decodes byte by byte and error by error.

## Broader Decode

- **Irreversible 9/7 at every precision.** Components above 24 bits, which
  rc.4 refused, decode in f64 (T1 through 64-bit coefficients, f64 inverse
  9/7 and ICT); up to 24 bits the f32 path is unchanged. Kakadu 8.4.1's 28-
  and 30-bit irreversible streams decode within 115 and 423 levels of
  `kdu_expand`'s own output, which synthesizes in single precision.

## Faster Wide Encoder

- `zraw-to-j2k` codes the blocks of a tile on all threads and splits the
  wide 5/3 transform over them: a 34-bit 2000x1500 three-component encode
  drops from 8.8 s to 0.6 s at 20 threads, with byte-identical output.

## Measurement

- `tools/win_affinity_run.zig` confines a decoder to a processor mask
  through a job object, and `tools/win_pmc_record.ps1` with
  `tools/win_pmc_summary.py` record hardware counters per decode. They
  showed that an earlier per-core-type comparison let Kakadu run outside its
  mask; the corrected figures are in `docs/benchmarks.md`.

## Release Process

- As for rc.4, every archive was built and tested on a local machine:
  native Windows gates, and the Linux x86-64 and RISC-V 64 ReleaseFast suites
  in a Linux container (RISC-V under QEMU), with the official T.803 streams
  included in the corpus run (`tools/release_local.ps1`).
- **No macOS archive** is published for this candidate: hosted Actions
  minutes, which the native macOS build needs, are exhausted, and a
  cross-built binary could not be tested here. macOS users can build from
  source with Zig 0.17.

## Release Candidate Policy

The CLI and Zig API remain unstable before 1.0. This is not a general JP2/JPX,
camera RAW, or HDR converter. Each input adapter has a deliberately narrow
documented envelope; old-style or progressive JPEG, CCITT, LZMA, and ZSTD
TIFF compression, Adam7 PNG, CFA/demosaicing, compressed or tiled EXR,
general ICC transforms, extended XMP, and semantic metadata rewriting remain
unsupported. JP2 metadata payloads are preserved but are not yet restored into
TIFF output.

The project's 100/100 ISO engineering scorecards are internal coverage tools,
not formal ISO conformance certification; passing the T.803 streams is
evidence, not certification. The binaries are unsigned; verify the platform
archive against `SHA256SUMS`. Every archive contains identical `z2000` and
`z2k` executables for the long and short command names.
